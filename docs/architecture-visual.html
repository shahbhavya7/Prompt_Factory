SACE — the prompt-memory engine behind Maya

Semantic Adaptive Context Engine: a flat pool of retrievable rules replaces one monolithic system prompt. Every turn asks memory which rule governs, sends only that rule to the model, and checks the reply actually came from it. This page draws the mechanism end to end — retrieval, generation, grounding, and the offline loop that grows the pool from real calls.

The whole loop, in one picture

Two front ends — a voice call and a Streamlit chat — both hand the same three inputs to one Engine: the caller's state, the conversation history, and this turn's message. Everything downstream is shared code, so a voice caller and a chat tester are governed by identical logic.

Retrieval: one flat pool, two decisions

There is no stage machine and no branch tree. Every rule is one row in Postgres, found by cosine similarity against a short cue — the caller-side situation that should surface it — never against the rule's own scripted text. Two semantic decisions happen per turn, both against the same query vector.

1 · does the message name an intent?

The caller's message alone (never blended with prior context) is scored against kb.INTENT_EXEMPLARS — short caller-phrased examples per label, e.g. dnc, busy, callback_request. Above cosine 0.45 the closest label wins; below it, no intent.

2 · which single rule governs?

With an intent: the nearest rule carrying that intent column — one row, nothing else in scope. Without one: the two nearest rules where intent IS NULL — the closest governs, the runner-up is reference-only context, never a source of content.

The grounding gate — checking the model told the truth

A structured LLM call returns {intent, reply, call_should_end, extracted_fields}. Nothing forces the reply to actually come from the governing rule — so it's checked, the same way in chat and voice, before it's trusted.

(b) spliced — checked first

If the reply's cosine to a reference rule beats its cosine to the governing rule, the model took a sentence from the wrong place — checked before the grounding floor because a splice can still clear 0.45 against its stolen source.

(a) ungrounded — the floor

Below cosine 0.45 against the governing rule, the reply isn't traceable to it at all — the model improvised. One regeneration is granted, with the specific reason appended to the prompt as a correction block.

Still failing after that one regeneration → shipped anyway, but logged as ungrounded/spliced in the turns table rather than silently forced through. A terminal rule additionally forces call_should_end=true regardless of what the model returned, and strips any sentence trailing the close — the model doesn't get a vote on whether the call is over.

The pool itself

One chunks table. A seed rule is hand-authored at boot; a learned rule is written later by the consolidator, through the exact same insert path — retrieval cannot tell the two apart, and isn't supposed to.

intent = NULLreachable only by plain semantic similarity — the general conversational flow (opening, identity check, benefits question, hold/retry, wrong number, medical emergency…)
intent = "dnc" / "abuse"priority: critical always outranks distance within its intent — a compliance close must never lose to a closer-scoring learned paraphrase
intent = "busy" / "elsewhere" / …priority: high the 12 other routable labels — callback, redirect, language, pricing, clinical, AI-question, and so on
terminal = truespeaking this rule ends the call — enforced in code after the model replies, not requested of it
exclusive = truenothing else may share the turn — the reference list is emptied, so there's no second rule to splice from

The offline loop — how the pool grows

Runs once, after a call ends — never mid-turn. Takes a finished transcript in, and either a new rule or a flagged review row comes out; nothing is silently applied and nothing is silently dropped.

Why a pool instead of one prompt

The comparison this whole design is answering: a monolithic system prompt carrying every branch, versus one retrieved rule per turn.

before monolith

One system prompt holds every stage, every branch, every edge case — pinned at 5,782 tokens, sent whole on every single turn whether or not it's relevant to what the caller just said.

now retrieved pool

Stable core + exactly one governing rule (+ ≤1 reference rule) — measured at roughly 1,000–1,350 tokens/turn, a 77–82% cut against the monolith, computed fresh per turn and reported as saved_pct in the debug trace.
